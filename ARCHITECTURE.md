## 8.2 — MCP Architecture Overview

```
Endpoint:   POST /api/mcp
Protocol:   JSON-RPC 2.0
Auth:       Bearer token (MCP_SECRET_KEY)
            ⚠️  Auth check is currently COMMENTED OUT in route.ts:191
            The endpoint is publicly writable until this is re-enabled.

Validation: ajv (strict schemas from content-schema.ts)
Sanitize:   sanitize-html applied recursively to all string values before validation
Audit:      Every tool call logged to mcp_audit_log table (win or fail)
History:    update_section_content saves previous value to content_history before overwrite
Rollback:   rollback_section restores from content_history (archives current first)
```

### All 13 MCP Tools

| Tool | Description |
|---|---|
| `list_pages` | Returns all section IDs grouped by page prefix |
| `get_section_schema` | Returns the AJV JSON Schema for a section |

## 8.4 — Database Schema

### `site_content`
Stores all CMS content keyed by section ID.

| Column | Type | Notes |
|---|---|---|
| `section_id` | text (PK) | e.g. `home-hero-heading` |
| `content_data` | jsonb | The full content payload (validated against content-schema.ts) |
| `updated_at` | timestamptz | Set on every upsert |

### `posts`
Blog posts table.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | Auto-generated |
| `title` | text | min 5, max 200 chars |
| `slug` | text (unique) | `^[a-z0-9]+(?:-[a-z0-9]+)*$` pattern |
| `category` | text | Enum: ENGINEERING, DESIGN, PERFORMANCE, STRATEGY, AI |
| `seo_description` | text | min 100, max 170 chars |
| `featured_image` | text (nullable) | URI format |
| `content_blocks` | jsonb | Array of `ContentBlock` objects |
| `status` | text | Enum: draft, scheduled, published |
| `published_at` | timestamptz (nullable) | Set automatically on first publish |
| `created_at` | timestamptz | Set at creation |

**ContentBlock types:** `paragraph`, `heading`, `list`, `quote`, `image`, `code`

### `content_history`
Tracks every version of a site section before it is overwritten.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | Referenced by `rollback_section` |
| `section_id` | text | FK-style reference to site_content |
| `content_data` | jsonb | Snapshot of the content before update |
| `changed_by` | text | Currently `'mcp-update'` or `'mcp-rollback-archive'` |
| `created_at` | timestamptz | |

### `mcp_audit_log`
Immutable log of every MCP tool invocation.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | |
| `tool_name` | text | e.g. `update_section_content` |
| `arguments` | jsonb | The args passed to the tool |
| `success` | boolean | |
| `error_message` | text (nullable) | |
| `created_at` | timestamptz | |

### `contact_inquiries`
Stores lead form submissions from `/contact`.

| Column | Type | Notes |
|---|---|---|
| `full_name` | text | |
| `email` | text | |
| `phone_number` | text | Defaults to `'N/A'` if not provided |
| `message` | text | |
| `created_at` | timestamptz | |

### `user_entitlements`
Populated by the Razorpay payment webhook for template purchases.

| Column | Type | Notes |
|---|---|---|
| `email` | text | Buyer email |
| `order_id` | text | Razorpay order ID |
| `payment_id` | text (unique, onConflict key) | Razorpay payment ID |
| `amount` | numeric | In INR (converted from paise) |
| `status` | text | `'active'` on successful payment |
| `source` | text | `'razorpay'` |
| `created_at` | timestamptz | |

## 8.6 — Data Flow Diagram

### Frontend Content Read Flow
```
Page loads (SSR)
  → getSectionContent(sectionId, fallback)  [src/lib/getContent.ts]
    → supabaseAdmin.from('site_content').select().eq('section_id', ...).single()
      → If found: return content_data (jsonb, cast to typed interface)
      → If error/empty: return fallback (hardcoded in the page file)
  → Section content passed as variables directly into JSX
  → Inline styles from *-style sections applied to <section> containers
```

### MCP Content Write Flow
```
AI/n8n client
  → POST /api/mcp
    → Body: { jsonrpc: "2.0", id, method: "tools/call",
               params: { name: "update_section_content",
                         arguments: { section_id, content_data } } }
    → Auth check: Authorization: Bearer <MCP_SECRET_KEY>
      ⚠️  Currently bypassed (commented out)
    → sanitizePayload(content_data)     [recursive sanitize-html]
    → ajv.compile(CONTENT_SCHEMAS[section_id].schema)(sanitizedData)
      → If invalid: return JSON-RPC error -32602 with AJV error details
    → supabaseAdmin.from('site_content').select() [save current to history]
    → supabaseAdmin.from('content_history').insert()
    → supabaseAdmin.from('site_content').upsert()
    → logAudit(tool, args, success)
    → Return: { jsonrpc: "2.0", id, result: { content: [{ type: "text", text: "..." }] } }
  → Next page load reads updated content from Supabase
```

### Contact Form Submission Flow
```
User fills LeadForm ("use client")
  → react-hook-form + zod validation (client-side)
  → fetch('/api/contact', { method: 'POST', body: JSON.stringify({name, email, phone, message}) })
    → Basic validation (name, email, message required)
    → supabaseAdmin.from('contact_inquiries').insert([contactData])
    → Return { success: true } or error JSON
  → LeadForm shows success state or error message
```

### Razorpay Payment Flow
```
User clicks "Purchase Blueprint" on templates page
  → [Frontend checkout — not implemented yet, links to /checkout/* routes]

Payment captured event
  → Razorpay → POST /api/webhook/razorpay
    → Verify HMAC-SHA256 signature (RAZORPAY_WEBHOOK_SECRET)
    → On payment.captured:
      → supabaseAdmin.from('user_entitlements').upsert({ email, order_id, amount, ... })
```

### Telegram Bot Flow
```
User messages @YourSiteBot
  → Telegram → POST /api/webhook/telegram
    → Voice: logs file_id, queued for future IndicConformer STT pipeline
    → Text /start: logs chat_id, future Walled Garden onboarding
    → Returns 200 always (prevents Telegram retries)
```

## 8.8 — Known Patterns & Conventions

### Fallback Content Pattern
Every page defines `const fallback*` constants at the top of the file. These are hardcoded TypeScript objects that mirror the production content. If Supabase is unreachable or a section hasn't been seeded, the site renders using these fallbacks. This is the graceful degradation strategy.

```typescript
// Pattern in every page:
const heroHeading = await getSectionContent('home-hero-heading', fallbackHeroHeading);
```

### Style Sections
Every page region has a corresponding `*-style` section ID. These sections use `STYLE_SCHEMA` which allows overriding background color, image, overlay, text color, padding, font size, and text alignment. Applied as inline styles on the `<section>` element:

```tsx
<section style={{
  backgroundColor: heroStyle.backgroundColor,
  color: heroStyle.textColor,
  textAlign: heroStyle.textAlign as any,
  paddingTop: heroStyle.paddingTop,
  paddingBottom: heroStyle.paddingBottom,
}}>
```

### Server vs Client Component Pattern
- **Server Components (default):** All pages, layouts, CTASection, Brand, BlockRenderer, WhatsAppFab — can be async, call `getSectionContent`, use `supabaseAdmin`
- **Client Components (`'use client'`):** NavBar, Dock, LeadForm, ThemeToggle, SocialLinks, Particles, InfiniteMovingCards, SocialIcon — handle interactivity, browser APIs, motion

The marketing layout (`(marketing)/layout.tsx`) is a Server Component that fetches global nav/footer data and passes it as props to Client Components (NavBar receives `items`, SocialLinks receives `items`). This avoids Client Components making DB calls.

### Blog Post Structure
Blog posts use a typed `content_blocks` array (stored as jsonb) instead of raw HTML/Markdown. Each block has a `type` field (`paragraph`, `heading`, `list`, `quote`, `image`, `code`) rendered by `BlockRenderer.tsx`. This makes posts fully structured and editable via MCP without an HTML parser.

### Contact Form Flow
The `LeadForm` is a `'use client'` component that validates locally with zod before POSTing to `/api/contact`. The API route uses `supabaseAdmin` (bypasses RLS) to insert into `contact_inquiries`. No email sending is wired up — it's DB-only capture.

### MCP Authentication Status
**The bearer token check at line 191 of `src/app/api/mcp/route.ts` is commented out.** This means the MCP endpoint accepts any POST request from any origin without authentication. This must be re-enabled before going to production. The check is:

```typescript
// if (authHeader !== `Bearer ${process.env.MCP_SECRET_KEY}`) {
//   return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
// }
```

### Admin Dashboard Status
The admin dashboard at `/app/*` has no authentication guard. The `AdminLayout` is a simple Server Component with a sidebar — there is no session check, no middleware, no Supabase Auth integration. The blog editor at `/app/blog/new` is a static UI prototype with no wired submit action. The admin area is not production-ready.

### Seeding Content
Run `pnpm tsx scripts/seed-mcp.ts` to populate all 60 sections with default content. The script uses the service role key and upserts with `onConflict: 'section_id'`, so it is safe to re-run (idempotent).

### Artifacts to be Aware Of
- `src/app/(marketing)/footer>` and `src/app/(marketing)/header>` — these are empty files, not directories. They appear to be shell redirection accidents (`echo > header>`). They do not affect routing or functionality.
- `src/app/(marketing)/test.tsx` — likely a scratch file, not a route.
- The admin dashboard stats on `/app` are hardcoded placeholder numbers, not live analytics.
